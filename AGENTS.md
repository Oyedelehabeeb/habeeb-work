# AGENTS.md

## 1. Project Identity

This project is the personal portfolio of Habeeb Oyedele, a Web & Mobile Product Engineer.

This is not intended to be a generic developer portfolio, digital résumé, or gallery of technology logos.

It is a production-quality personal brand and product-engineering portfolio whose primary purposes are to:

- demonstrate the quality and depth of Habeeb's work
- communicate strong product and engineering judgement
- showcase selected public projects through thoughtful case studies
- communicate web and mobile development capabilities
- build trust with potential clients, founders, hiring managers, and collaborators
- make it easy for interested people to start a conversation

The portfolio itself should demonstrate the same level of engineering and design quality expected from the products being showcased.

---

## 2. Positioning

Primary positioning:

**Web & Mobile Product Engineer**

The portfolio should communicate expertise across modern web and mobile product development while preserving a clear frontend/product-engineering identity.

Avoid positioning that makes the user appear limited to:

- landing-page development
- generic frontend implementation
- visual design only
- no-code development

Also avoid exaggerated titles or claims that cannot be demonstrated through the work.

---

## 3. Audience

The portfolio has two primary audiences.

### Potential clients and founders

They need to understand:

- what Habeeb can build
- whether he understands products rather than merely tickets
- whether his work is polished
- whether he can ship real applications
- what kinds of projects he works on
- how to contact him

### Recruiters and engineering teams

They need to understand:

- technical capabilities
- stack
- responsibilities
- architectural thinking
- project complexity
- web/mobile experience
- production experience
- how to access résumé, GitHub, LinkedIn, etc.

The portfolio must serve both audiences without creating separate experiences for them.

Only make claims that can be supported.

Do not invent:

- user numbers
- conversion improvements
- revenue
- performance improvements
- research studies
- client testimonials
- business outcomes
- team composition
- responsibilities

If a useful metric is unavailable, describe the actual engineering or product result instead.

## 13. Visual Philosophy

Desired direction:

**Editorial portfolio × premium product showcase × restrained technical personality**

The portfolio should feel:

- intentional
- mature
- modern
- distinctive
- highly polished
- product-oriented
- editorial
- technically sophisticated

Avoid:

- generic developer templates
- gratuitous gradients
- purple/blue SaaS clichés
- glassmorphism everywhere
- floating technology logos
- code-window hero clichés
- excessive terminal aesthetics
- gimmicky developer motifs
- excessive cards
- visual noise

---

## 14. Visual References

Any screenshots, websites, videos, or visual references supplied during development are:

**inspiration and design references only.**

They are NOT specifications to replicate.

Never recreate a supplied design pixel-for-pixel.

Instead analyze references for principles such as:

- hierarchy
- typography
- spacing
- grid
- composition
- image treatment
- project presentation
- case-study storytelling
- interaction
- motion
- responsive behavior
- navigation
- visual rhythm

Synthesize useful principles into an original design language appropriate to Habeeb's portfolio.

Do not clone individual portfolio websites.

---

## 15. Color Direction

Use a restrained neutral foundation that allows project imagery to carry significant color.

Initial direction:

- ink / near-black
- warm off-white
- neutral gray scale
- one deliberate brand accent

Exact colors are not locked until reference analysis is complete.

Avoid choosing a stereotypical developer palette by default.

---

## 16. Typography

Typography is a major part of the visual identity.

The design should explore:

- strong display typography
- excellent editorial hierarchy
- readable body typography
- controlled contrast between display and supporting type
- high-quality numerical/metadata presentation

Do not choose fonts purely because they are common developer-portfolio defaults.

Font decisions should follow reference analysis and licensing/performance considerations.

---

## 17. Layout

Favor:

- strong grids
- editorial compositions
- generous whitespace
- full-width project imagery where useful
- varied project layouts
- clear visual hierarchy

Avoid putting every item into a rounded card.

The interface should feel art-directed rather than generated from repeated component templates.

---

## 18. Project Media

Project imagery is central to the portfolio.

Use high-quality:

- desktop screenshots
- mobile screenshots
- browser compositions
- device mockups
- cropped interface details
- product videos where useful
- diagrams where useful

Do not use mockups merely for decoration.

Media should help explain the product.

Different projects should receive media treatment appropriate to their platform.

For example, chopNG should emphasize mobile presentation rather than desktop browser mockups.

---

## 19. Motion and Interaction

Motion should demonstrate frontend craftsmanship while remaining functional.

Potential techniques:

- project image reveals
- refined hover states
- route transitions
- typography reveals
- subtle parallax
- image masking
- project previews
- scroll-based storytelling
- device transitions

Do not:

- hijack scrolling
- block the site behind intro animations
- impair navigation
- sacrifice accessibility
- overload every section with animation

Respect `prefers-reduced-motion`.

---

## 20. Responsive Design

Mobile is a first-class design target.

Do not merely compress desktop layouts.

Pay particular attention to:

- project imagery
- typography
- navigation
- case-study storytelling
- horizontal media compositions
- touch interactions
- contact conversion

The mobile portfolio should feel deliberately designed.

---

## 21. Accessibility

Accessibility is mandatory.

Use:

- semantic HTML
- keyboard-accessible interactions
- visible focus states
- sufficient contrast
- meaningful alt text
- reduced-motion support
- accessible navigation
- accessible forms

Do not make important content dependent on hover.

---

## 22. Performance

Visual ambition must not destroy performance.

Prioritize:

- optimized imagery
- responsive image formats
- controlled JavaScript
- lazy loading where appropriate
- minimal layout shift
- efficient animation
- strong Core Web Vitals

Measure performance rather than assuming it.

---

## 25. Technical Architecture

The exact stack must be confirmed before implementation.

Prefer the simplest architecture that provides:

- excellent SEO
- fast rendering
- high-quality image handling
- smooth navigation
- sophisticated interactions
- maintainability
- easy project-content updates

Do not introduce databases, authentication, CMS infrastructure, realtime systems, or backend services without an actual requirement.

---

## 26. Content Architecture

Project/content information should be structured rather than scattered throughout UI components.

Prefer a reusable content model for:

- projects
- roles
- technologies
- links
- project metadata
- case-study sections
- project media

The implementation should make adding future projects straightforward without forcing every project into an identical visual template.

---

## 27. Future Expansion

The architecture should allow future addition of:

- new projects
- additional case studies
- writing/notes
- testimonials if genuine testimonials become available
- project categories
- résumé updates

Do not build unused systems for these possibilities now.

---

## 28. Development Workflow

For major features:

1. understand the requirement
2. inspect provided references
3. identify ambiguity
4. propose a solution
5. get approval for significant visual/architectural decisions
6. implement
7. test responsive behavior
8. test accessibility
9. review performance
10. review visual consistency
11. refine
12. proceed

Do not autonomously redesign the entire site after major decisions have been approved.

---

## 29. Questions Before Assumptions

Ask before making consequential decisions around:

- final branding
- primary visual direction
- fonts
- major animation library
- CMS
- backend services
- analytics
- contact infrastructure
- project ordering
- project claims/content
- theme strategy

Do not ask unnecessarily about minor implementation details.

---

## 30. Quality Standard

This portfolio should itself be one of Habeeb's strongest projects.

The target is not:

> "A good developer portfolio."

The target is:

> **A world-class product engineer portfolio that makes the quality of the work immediately obvious and turns serious visitors into conversations.**

Prioritize quality over feature count.
